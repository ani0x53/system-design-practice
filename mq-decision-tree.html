Starting point
Why do you need async messaging?
The core reason you're reaching for a queue determines which tool fits. Don't pick Kafka because it's popular — pick it because your problem needs a distributed commit log.
Signs you need a queue

Producer is faster than consumer. Downstream services go down and you lose work. Synchronous calls create cascading failures. You need to process the same event in multiple services.

Signs you might NOT

You need a response from the downstream service. Total latency under 50ms matters. You have <100 events/s and no reliability needs. You're adding a queue "just in case".

Decoupling — fire-and-forget work
Send emails, resize images, charge payments — work that doesn't need to block the request. Producer shouldn't know or care about consumer speed.
Classic pattern: web request → queue → worker pool
2
Fan-out — one event, many consumers
A single event (user signup, order placed) needs to trigger actions in 3+ independent services. Each consumer processes independently.

Your downstream (DB, API, payment gateway) can't handle peak load. You need to smooth writes and protect fragile backends.

What's the downstream bottleneck?
The thing you're protecting determines the buffering strategy. A database handles backpressure differently than a third-party API with rate limits.
1
Database — write-heavy, can't drop requests
Your Postgres/MySQL can't keep up with write volume. You need a buffer to absorb spikes and guarantee every write eventually lands in the DB.
Kafka → batch consumer → DB: smooth 10:1 peak-to-baseline ratio
2
External API — respect rate limits
Calling Stripe, Twilio, or a partner API that allows 100 req/s. Need to queue work and drain at a controlled rate with retry on 429s.

3
Internal service — prevent cascade failure
A slow internal service (ML inference, PDF generation) backs up and causes cascading timeouts. Need to shed load gracefully.
Queue + bounded concurrency: control in-flight work, fail fast on overflow

Can you afford to lose any writes?
This determines how much machinery you need. "Smoothing spikes" is a different problem than "guaranteed zero-drop writes under any failure scenario."
1
Zero data loss — every write must land in the DB
Financial transactions, order placements, audit events. If the app accepted the request, it MUST eventually be written. Losing a write means losing money or breaking compliance.
Requires: acks=all, idempotent producer, transactional outbox or Kafka transactions
2
Best-effort — smooth spikes, some loss on catastrophic failure OK
Analytics events, clickstream, metrics, logs. Losing a few events during a broker crash is acceptable. Optimize for throughput and simplicity.
Simpler setup: acks=1, no outbox pattern, just Kafka as a buffer
Buffering → Zero-drop → step 3 of 3
Where does the write originate?
The guarantee strategy depends on whether the write starts in your application code (API request) or is already committed to a database (sync from DB to downstream).
1
API request — app receives request, must guarantee DB write
User places an order via API. You need to acknowledge it, buffer it through Kafka, and guarantee it reaches the database. The hard part: what if Kafka publish fails after you've already responded 200?
Transactional outbox pattern: write to DB + outbox in one transaction
2
DB change — data is in DB, must propagate to other systems
Data is already safely in your primary DB. You need to reliably stream changes to Elasticsearch, cache, warehouse, or other services without dual-write bugs.
CDC (Debezium): reads the WAL, zero data loss, no app code changes

The problem

Your API receives a write request. You need to: (1) acknowledge it to the user, (2) buffer it in Kafka, and (3) guarantee it eventually reaches the database. The naive approach — publish to Kafka, then write to DB — fails because either step can crash independently. You get ghost writes (in Kafka but not DB) or lost events (in DB but not Kafka). This is the dual-write problem.

The solution: Transactional Outbox

Instead of publishing to Kafka directly, write both the business data AND the event to the same database in a single ACID transaction. A separate process (the "relay") polls the outbox table and publishes events to Kafka. Since the business write and the event are in the same transaction, they either both commit or both rollback. The relay is idempotent — if it crashes, it retries from the last published offset. Zero data loss.

Architecture

// ✗ WRONG: dual-write (either can fail independently) API → publish to Kafka // what if this succeeds... → write to Postgres // ...but this fails? ghost event in Kafka // ✓ CORRECT: transactional outbox API → BEGIN TRANSACTION INSERT INTO orders (...) // business data INSERT INTO outbox (topic, key, payload) // event COMMIT // atomic — both or neither Relay (polling or CDC) → reads outbox table → publishes to Kafka → deletes processed rows Kafka → Batch consumer (idempotent) → downstream systems

Outbox table schema

CREATE TABLE outbox ( id BIGSERIAL PRIMARY KEY, topic TEXT NOT NULL, -- Kafka topic name key TEXT, -- partition key (e.g. order_id) payload JSONB NOT NULL, -- event data created_at TIMESTAMPTZ DEFAULT NOW(), published BOOLEAN DEFAULT FALSE -- relay marks true after publish ); -- Index for the relay to poll efficiently CREATE INDEX idx_outbox_unpublished ON outbox (id) WHERE published = FALSE;

Relay options

Polling relaySELECT from outbox WHERE published=false
CDC relay (Debezium)reads outbox via WAL — no polling
Polling interval100ms–1s typical
Throughput10k–50k events/s (CDC relay)
Debezium can read the outbox table via CDC — this eliminates polling entirely. Debezium reads the WAL, captures outbox inserts, and publishes to Kafka. This is called the "outbox + CDC" pattern and is the most robust option.

Kafka producer settings for zero data loss

enable.idempotencetrue (dedup retries)
min.insync.replicas2 (survive 1 broker loss)
retriesMAX_INT (retry forever)
max.in.flight.requests5 (safe with idempotence)

Consumer side: idempotent writes to DB

// Consumer must be idempotent — messages CAN be delivered >1 time // Option 1: Upsert with natural key INSERT INTO orders (order_id, ...) VALUES (...) ON CONFLICT (order_id) DO NOTHING; // Option 2: Dedup table INSERT INTO processed_events (event_id) VALUES ('evt-789') ON CONFLICT DO NOTHING; -- if this fails, skip the event // Option 3: Consumer offset in same DB transaction BEGIN INSERT INTO orders (...); UPDATE consumer_offsets SET offset = 12345 WHERE partition = 3; COMMIT // exactly-once: process + offset commit are atomic
The outbox table will grow forever if you don't clean it up. Delete or archive published rows on a schedule. A common pattern: keep 24h of published events, delete older rows in batches during off-peak hours.
Ordering guarantee: the outbox relay publishes events in outbox ID order. But if you have multiple relay instances, you need to partition by key to maintain per-entity ordering in Kafka.

When NOT to use the outbox pattern

If your write doesn't need a database transaction (pure event append), skip the outbox — just use Kafka directly with acks=all and idempotent producer. The outbox exists specifically for the case where you need atomicity between a DB write and an event publish. Don't pay the complexity cost if you don't have the dual-write problem.

Why SQS Standard

For simple decoupling where you don't need ordering or exactly-once semantics, SQS Standard is the lowest-friction option. No brokers to manage, no capacity planning, no rebalancing. You pay per request. It scales to effectively unlimited throughput automatically. Your consumers must be idempotent because messages can be delivered more than once.

Why SQS FIFO

When you need per-entity ordering (all events for user_123 processed in order) and exactly-once delivery without building dedup yourself, FIFO queues handle this at the infrastructure level. The tradeoff is lower throughput — 3k msg/s without batching, up to 30k/s with high-throughput mode. Use MessageGroupId to partition ordering by entity.

Key numbers

Throughput3k msg/s (30k batched)
Deliveryexactly-once
Orderingstrict per MessageGroupId
Deduplication5-min dedup window
Cost$0.50/M requests
Throughput is per-queue, not per-group. If you have 1000 message groups but send all to one FIFO queue, total throughput is still capped at 3k/s (or 30k/s in high-throughput mode). Shard across multiple queues if needed.

MessageGroupId pattern

// Group by entity to get per-entity ordering sqs.sendMessage({ QueueUrl: "https://sqs...fifo", MessageBody: payload, MessageGroupId: "order-456", // all order-456 events in order MessageDeduplicationId: "evt-789" // prevent duplicates within 5 min })
A blocked message group blocks only that group, not the entire queue. Other groups continue processing independently. This is the key insight that makes FIFO queues usable at scale.

Why RabbitMQ

RabbitMQ is a "smart broker, dumb consumer" model — the broker does the routing. It excels when you need exchange types (direct, topic, fanout, headers), per-message TTL, priority queues, delayed messages, and dead-letter exchanges. It pushes messages to consumers, giving you the lowest latency of any traditional broker. The tradeoff: messages are deleted after acknowledgment — no replay.

Key numbers

Throughput~30k msg/s
Latency<1ms publish
Routingexchanges, binding keys
ProtocolAMQP, MQTT, STOMP
Deliveryat-least-once (ack-based)
Replaynot supported
Clusteringquorum queues (Raft)
Strengths

Flexible routing patterns. Priority queues. Per-message TTL. Dead-letter exchanges. Management UI. Multi-protocol. Lowest latency.

Weaknesses

No replay/rewind. Slower than Kafka at high throughput. Memory pressure with millions of queued messages. Complex HA setup.

RabbitMQ degrades badly when queues grow deep (>100k messages). If consumers can't keep up, messages pile in memory/disk and the broker slows down. Monitor queue depth aggressively.

Apache Kafka

Why Kafka for fan-out

Kafka's consumer group model is the gold standard for fan-out with independent consumption. Each consumer group gets all messages on a topic but tracks its own offset. The analytics team can be hours behind while the billing team processes in real time — neither blocks the other. Messages are retained on disk, so a new service can join and replay from the beginning. This is fundamentally different from traditional queues where messages are deleted on consumption.

Key numbers

Throughput1M+ msg/s per broker
Latency (acks=1)~2ms
Latency (acks=all)~5–15ms
Retentionconfigurable (days–forever)
Orderingstrict per partition
Consumer groupsunlimited
Replayseek to any offset/timestamp
Kafka does well

High throughput. Fan-out to N consumer groups. Event replay. Long retention. Ordering per partition key. Horizontal scaling via partitions.

Kafka does NOT do

Per-message routing/filtering (consumer reads all). Priority queues. Delayed delivery. Message-level TTL. Sub-ms latency.

Partition count = max parallelism per consumer group. If you have 12 partitions, at most 12 consumers in a group can read in parallel. Over-partition early: it's cheap and hard to change later.

Fan-out architecture

Topic: order-events (partitions: 12, replication: 3) // Each consumer group independently reads ALL messages Group: billing-service → 3 consumers → processes payments Group: inventory-service → 3 consumers → updates stock Group: notification-service → 2 consumers → sends emails Group: analytics-pipeline → 1 consumer → ETL to warehouse // Key insight: groups are independent. // Analytics can lag 2 hours without affecting billing.
Partition key design matters. All messages with the same key go to the same partition (same consumer). Choose a key that distributes evenly — user_id or order_id, not country_code.

When to add stream processing

Plain Kafka consumers read events one at a time. Stream processing frameworks let you do real-time joins (enrich orders with user data), sliding/tumbling window aggregations (requests per minute), stateful transformations (session windows), and exactly-once semantics across input → process → output. You have three main options, each with different tradeoffs.

Framework comparison

Kafka Streamslibrary (JVM), no cluster needed
Apache Flinkmost powerful, its own cluster
ksqlDBSQL over streams, good for prototyping
Kafka Streams

Java library. Runs in your app — no separate cluster. Good for moderate complexity: joins, aggregations, repartitioning. Scales with your app instances.

Apache Flink

Separate cluster. Best for complex event processing, large-scale joins, exactly-once across systems, and advanced windowing. Steeper ops overhead but most capable.

Start with Kafka Streams if you're already on JVM. It's just a library — no cluster to deploy. Move to Flink when you need cross-system exactly-once, complex event processing, or Python/SQL interfaces.

Windowed aggregation example

// Kafka Streams: 5-minute tumbling window stream .groupByKey() .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5))) .count() .toStream() .to("request-counts-per-5min"); // Flink SQL equivalent SELECT user_id, COUNT(*) AS cnt, TUMBLE_START(event_time, INTERVAL '5' MINUTE) AS window_start FROM clickstream GROUP BY user_id, TUMBLE(event_time, INTERVAL '5' MINUTE);

Why SNS + SQS

The simplest fan-out pattern on AWS. Publish once to an SNS topic. Each subscribing SQS queue gets a copy independently. Each queue has its own DLQ, retry policy, and consumer. Adding a new subscriber is just creating a new SQS queue and subscribing it — zero code changes to the producer. SNS also supports message filtering, so subscribers can receive only the events they care about without client-side filtering.

Architecture

Producer → SNS Topic: order-events ├→ SQS: billing-queue → Billing Lambda ├→ SQS: inventory-queue → Inventory service ├→ SQS: notification-queue → Email Lambda └→ SQS: analytics-queue → Firehose → S3 // SNS filter policy (subscriber only gets matching events) { "event_type": ["order_shipped", "order_delivered"] }

Why RabbitMQ fanout

A fanout exchange sends every message to every bound queue — simple broadcast. Unlike SNS+SQS, you get AMQP protocol support, on-prem deployment, and can combine with topic/headers exchanges for sophisticated routing in the same broker. Each bound queue is an independent consumer with its own acknowledgment and retry semantics. For multi-cloud or on-prem, this is the go-to fan-out pattern.

Exchange types for different fan-out needs

fanoutbroadcast to all queues
topicroute by pattern (order.*)
directroute by exact key
headersroute by message headers

Setup pattern

// Declare fanout exchange channel.exchangeDeclare("order-events", "fanout", durable: true); // Each service creates its own queue and binds channel.queueDeclare("billing-q", durable: true); channel.queueBind("billing-q", "order-events", ""); channel.queueDeclare("inventory-q", durable: true); channel.queueBind("inventory-q", "order-events", ""); // Producer publishes once — both queues get a copy channel.basicPublish("order-events", "", props, body);
Need pattern-based filtering? Use a topic exchange instead. Binding key "order.shipped" matches routing key "order.shipped". Binding "order.*" matches any order event.

Why CDC with Debezium + Kafka

CDC reads your database's transaction log (Postgres WAL, MySQL binlog) and streams every INSERT/UPDATE/DELETE as an event to Kafka topics — one topic per table. Downstream consumers (Elasticsearch, Redis, data warehouse) stay in sync without dual-write bugs. The critical insight: your database already records every change in its WAL. CDC just exposes that log as a stream. No application code changes needed.

Key numbers

Throughput50k+ changes/s
End-to-end lag~100ms–1s typical
DB overhead~5% (reads WAL, no queries)
Supported DBsPostgres, MySQL, MongoDB, SQL Server
DeploymentKafka Connect connector
Never do dual writes (write to DB + publish to Kafka in app code). One will fail and you'll have inconsistency. CDC eliminates this problem — the DB write IS the event source.

Architecture

Postgres (WAL) → Debezium connector → Kafka ├→ topic: db.public.users ├→ topic: db.public.orders └→ topic: db.public.products // Downstream consumers db.public.orders → Elasticsearch (search index) db.public.orders → Redis (cache invalidation) db.public.orders → Snowflake (analytics)
Debezium captures the before and after state of each row change. This means consumers can compute diffs, detect deletions, and build accurate materialized views.
path: event streaming → CDC

Why EventStoreDB

EventStoreDB is designed specifically for event sourcing. Every event is appended to a stream (typically one stream per aggregate). It has built-in optimistic concurrency control, catch-up subscriptions for building projections, and a projections engine for cross-stream queries. Unlike Kafka, streams map 1:1 to business entities — stream "order-456" contains only events for that order. This is the right fit when your domain model is event-sourced and you want the tooling to match.

Event sourcing pattern

// Append events to a stream stream: "order-456" [0] OrderCreated { items: [...], customer: "user-789" } [1] PaymentReceived { amount: 149.99, method: "card" } [2] OrderShipped { tracking: "1Z999..." } // Rebuild current state: replay events 0→2 // Optimistic concurrency: append at expected version 2 // If another write happened, you get a conflict — handle it // Projection: subscribe to $all, filter OrderCreated events // Build a read model: "orders by customer" in Postgres/Redis

Why Kafka for event sourcing

At massive scale (millions of entities, billions of events), Kafka's throughput and ecosystem are hard to beat. Use compacted topics to retain only the latest state per key, or configure infinite retention to keep every event forever. The tradeoff: Kafka doesn't natively support per-entity concurrency control or per-entity streams — you partition by entity key and build optimistic concurrency in your application layer. This is more work but gives you Netflix/Uber-scale event sourcing.

Why Kafka as an event bus

In a microservices architecture, Kafka acts as the central event bus. Every service publishes domain events to Kafka topics. Any service — existing or future — can subscribe to any topic and build its own view of the data. This decouples services at the data level. Kafka Connect provides pre-built connectors to move data between Kafka and 100+ external systems (databases, S3, Elasticsearch, Snowflake) without writing code.

Kafka Connect200+ connectors (source & sink)
Schema RegistryAvro/Protobuf schema evolution

MirrorMakercross-datacenter replication

Event-driven architecture

// Services publish domain events User Service → topic: user-events (UserCreated, UserUpdated) Order Service → topic: order-events (OrderPlaced, OrderShipped) Payment Service→ topic: payment-events (PaymentProcessed, Refunded) // Kafka Connect sinks (no code) order-events → Elasticsearch (search) *-events → S3 via Firehose (data lake) user-events → Redis (cache warm) // New service joins 6 months later // Reads order-events from offset 0 — full replay Fraud Service ← topic: order-events (replay all history)
Schema Registry is critical for event-driven architectures. It enforces backward/forward compatibility — a producer can add a field without breaking existing consumers. Use Avro or Protobuf, not JSON.
An event bus is not a request-reply mechanism. If service A needs a synchronous response from service B, use HTTP/gRPC. Events are for "this happened" notifications, not "do this and tell me the result."

Recommended
Kafka — Write Buffer
Absorb write spikes, drain to the database at a steady rate
spike absorption batch consumer backpressure DB protection

Why Kafka as a write buffer

Your database can sustain 5k writes/s, but traffic spikes to 50k/s during peak. Instead of losing writes or overloading the DB, put Kafka in front. Kafka absorbs the spike (it can handle 1M writes/s to disk). A consumer drains Kafka at the database's comfortable rate, batching inserts for maximum efficiency. The writes are durably stored in Kafka — if the DB goes down, messages wait until it recovers. Zero data loss.

Key numbers

Kafka ingest rate1M+ msg/s
Batched DB writes10–50x faster than single inserts
Spike absorptionlimited only by disk
Recoveryconsumer resumes from offset
Data loss riskzero (acks=all, replication)

Architecture

// Without buffer (breaks under load) API → Postgres // 50k/s spike → DB overwhelmed → 504s // With Kafka buffer API → Kafka topic → Batch consumer → Postgres (absorbs 50k/s) (drains at 5k/s) (happy) // Batch consumer pattern while (true) { records = consumer.poll(Duration.ofMillis(500)); batch = records.collect(); // accumulate 100–1000 records db.batchInsert(batch); // single INSERT with 1000 rows consumer.commitSync(); // commit offset after DB write }
Batch inserts are 10–50x faster than individual inserts. 1000 rows in one INSERT statement vs 1000 individual INSERT statements — the difference is dramatic due to reduced round-trips and transaction overhead.
Consumer lag is normal and expected. The whole point is that consumers are slower than producers during spikes. Monitor lag — it should drain back to zero after the spike. If it never does, you have a sustained throughput problem, not a spike problem.
path: buffering → database protection

SQS — Rate-Limited Consumer
Queue work and drain at the API's rate limit
serverless rate limiting automatic retry DLQ for failures

Why SQS for API rate limiting

When calling rate-limited external APIs (Stripe: 100/s, Twilio: 1/s per number, partner APIs with quotas), SQS acts as a buffer. Your app enqueues requests instantly (no blocking). A consumer pulls from the queue at a controlled rate, respecting the API's limits. On 429 (rate limited) or 5xx errors, the message goes back to the queue automatically after the visibility timeout — built-in retry with no code. After N failures, it moves to a DLQ for investigation.

Key design decisions

Visibility timeoutset to 2x your processing time
Max receive count3–5 (then DLQ)
ConcurrencyLambda reserved concurrency = rate limit
Batch size1 for rate-limited APIs

Architecture

// Rate-limited API call pattern App → SQS Queue → Lambda (reserved concurrency: 10) → External API ↘ DLQ (after 3 failures) (rate limit: 10/s) // Lambda reserved concurrency = API rate limit // This naturally throttles consumption to match the API // For non-Lambda: use a consumer with a token bucket limiter = TokenBucket(rate=10, burst=10) while (true) { msg = sqs.receiveMessage(); limiter.acquire(); // blocks until token available result = callExternalAPI(msg); sqs.deleteMessage(msg); }
Lambda's reserved concurrency is the simplest rate limiter. Set it equal to the API's rate limit. SQS + Lambda handles all the retry, backoff, and DLQ logic for you.
path: buffering → external API

Recommended
Queue + Bounded Concurrency
Control in-flight work to prevent cascade failures
backpressure bounded concurrency graceful degradation load shedding

Why bounded concurrency

A slow internal service (ML inference: 500ms/request, PDF generation: 2s/request) becomes a bottleneck under load. Without backpressure, upstream services pile up connections, exhaust thread pools, and cascade-fail. The fix: put a queue in front and limit the number of in-flight requests to the slow service. This is the "leaky bucket" pattern — the queue absorbs bursts, consumers drain at a fixed rate, and if the queue fills up, you fail fast instead of failing slowly.

Key design principles

Max in-flight= service capacity (benchmark it)
Queue max depthbounded (reject when full)
Timeoutset on enqueue, not processing
Overflow behaviorfail fast with 503, don't block
Without backpressure

ML service slows down → requests queue in thread pool → upstream services timeout → retry storm → everything dies. Total outage from a slow dependency.

With backpressure

ML service slows down → queue absorbs burst → bounded workers process at capacity → queue full? → 503 immediately → upstream handles gracefully → partial degradation, not total failure.

Implementation options

// Option 1: SQS + Lambda (simplest) API → SQS → Lambda (reserved concurrency: 20) → ML Service // Lambda processes max 20 at a time // Option 2: In-process semaphore (no queue needed) semaphore = Semaphore(permits=20) if (!semaphore.tryAcquire(timeout=100ms)) { return 503 "Service busy, try later" } // Option 3: BullMQ / Celery (job queue with concurrency limit) queue = new Queue("ml-inference", { concurrency: 20 }) queue.add("predict", payload) // 21st job waits in queue, doesn't hit the ML service
The most common mistake: no queue depth limit. An unbounded queue just moves the OOM from the service to the queue. Always set a max depth and decide what happens when it's full (reject, drop oldest, or shed lowest-priority).
Circuit breakers (Hystrix, resilience4j) complement queues. The queue handles normal backpressure. The circuit breaker handles "service is completely dead" — it stops sending requests entirely and fails fast.
path: buffering → internal service → backpressure

Golden rules
01If you don't need replay, you probably don't need Kafka. SQS or RabbitMQ are simpler.
02Never dual-write (DB + queue in app code). Use CDC or transactional outbox.
03Make every consumer idempotent. Messages WILL be delivered more than once.
04Monitor consumer lag, not just throughput. Lag tells you if consumers are keeping up.
05Dead-letter queues are not optional. Every queue needs a DLQ and someone watching it.
06Schema evolution breaks things silently. Use Schema Registry with compatibility checks.
07A queue is not a database. Don't query it, don't store state in it, don't treat it as durable storage (except Kafka).
