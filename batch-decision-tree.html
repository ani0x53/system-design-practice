Starting point
What kind of data processing do you need?
Batch processing handles bounded datasets — you know the input size upfront. The right tool depends on data volume, compute type (CPU vs GPU), and latency tolerance.
Signs you need batch

Can tolerate minutes-to-hours latency. Processing complete datasets. Training ML models. Generating reports. Backfilling historical data. Cost-sensitive workloads where spot instances change the economics.

Signs you need streaming instead

Need sub-second latency. Event-by-event processing. Real-time dashboards. Fraud detection on individual transactions. Continuous data arrival with no natural "batch boundary".

dbt
Recommended
dbt (Data Build Tool)
SQL-first transforms where your data already lives
SQL-first warehouse-native version-controlled incremental

Why dbt

Transform where data already lives. No data movement. SQL + Jinja templating gives you modularity and DRY principles in SQL. Tests are built in — schema tests, data tests, freshness checks. Git-based workflow means PRs, code review, and CI/CD for your data transformations. Incremental models avoid full table scans by only processing new/changed rows.

Scale numbers

Full refresh on 1B rows (BigQuery)~5-15 minutes
Incremental on 10M new rows~30-60 seconds
Cluster costnone — warehouse compute only
Supported warehousesSnowflake, BigQuery, Redshift, Databricks, Postgres
Testingschema + data + freshness built-in

When dbt breaks down

Unstructured data (images, audio, PDFs) — dbt is SQL-only. Python-heavy transformations — though dbt Python models exist, they're limited and run as warehouse-side Python which is slow. Real-time / sub-minute freshness — dbt is batch, not streaming. Complex stateful transforms — anything that needs iteration or recursion doesn't fit the SQL model.

Incremental model example

-- models/orders_daily.sql {{ config( materialized='incremental', unique_key='order_id', partition_by={'field': 'order_date', 'data_type': 'date'} ) }} SELECT order_id, customer_id, SUM(amount) as total_amount, order_date FROM {{ ref('stg_orders') }} {% if is_incremental() %} WHERE order_date > (SELECT MAX(order_date) FROM {{ this }}) {% endif %} GROUP BY 1, 2, 4
dbt + BigQuery is probably the most cost-effective batch pipeline for structured data under 10TB. No clusters to manage, pay per query. A 1B-row incremental model costs pennies per run.
dbt doesn't handle orchestration well on its own. Pair with Airflow or Dagster for scheduling, alerting, and dependency management across projects. dbt Cloud adds scheduling but at $100/seat/month.

Why Spark

Distributed processing across 100s of nodes with automatic fault tolerance (RDD lineage). Handles semi-structured data natively — JSON, Parquet, Avro, ORC. Lazy evaluation + Catalyst query optimizer generate efficient execution plans. Exactly-once semantics with checkpointing. Rich ecosystem: Spark SQL, MLlib, GraphX, Structured Streaming. Python (PySpark), Scala, Java, R APIs.

1 TB Parquet join + aggregate~8-15 min on 20 nodes
Shuffle-heavy join on 10 TB~30-60 min on 50 nodes
Single node memory16-64 GB typical, spills to disk
Cost (EMR spot)~$0.03/node-hour
Cost (Databricks)~$0.10-0.40/DBU

Failure modes — what interviewers ask about

Data skew: One partition has 100x more data than others. One task takes 100x longer while 99 executors sit idle. Fix: salted keys, repartition, broadcast join for small tables (<100MB). Always check key distribution before large joins.

Shuffle spills: Insufficient memory during shuffle stage. Data spills from memory to disk, causing 10x slowdown. Fix: increase spark.sql.shuffle.partitions (default 200 is often too low), more executor memory, or pre-aggregate before the join.

Small files problem: 100k tiny Parquet files in S3. More time scheduling and opening files than actually computing. Fix: coalesce/repartition before write, run compaction jobs, use Delta Lake auto-optimize.

OOM on driver: Calling collect() on a large dataset pulls everything to driver memory. Fix: never collect() on large datasets, use distributed aggregations, increase driver memory only as last resort.

Stragglers: One slow task blocks the entire stage. Fix: speculative execution (spark.speculation=true) runs duplicate tasks, but doubles resource usage. Better: fix the root cause (skew, slow node).

Spark

Mature ecosystem. Excellent SQL support via Spark SQL. Python-friendly (PySpark). Huge community. Best for batch ETL and ad-hoc analytics.

Flink (batch mode)

Better for unified batch+stream. True exactly-once semantics. Lower latency for near-realtime. But smaller ecosystem, steeper learning curve, less Python support.

The #1 Spark failure in production is data skew. If your join key is user_id and 5% of users generate 80% of events, one executor processes 80% of the data while 99 others sit idle. Always check key distribution before large joins.
Consider Delta Lake or Apache Iceberg on top of Spark for ACID transactions, schema evolution, and time travel on your data lake. These table formats eliminate the small files problem and enable incremental processing.

Recommended
Lightweight ETL (Python + DuckDB / Pandas)
Single-node processing for sub-100GB datasets

Why lightweight ETL

For datasets under 100GB, you often don't need Spark at all. DuckDB is an in-process OLAP engine that processes Parquet files directly from S3 with zero infrastructure. It uses columnar execution, vectorized processing, and automatic parallelism. pandas works for <10GB in-memory. Polars is the modern alternative to pandas — 10-100x faster due to Rust backend and lazy evaluation.

Scale numbers

DuckDB: 50GB Parquet aggregation~30 seconds (r5.2xlarge)
pandas: same 50GB dataOOM or 10+ minutes
Polars: same 50GB data~45 seconds
Cluster setup time0 (no cluster)
Costsingle EC2 instance only

Failure modes

OOM: The main failure mode. No distributed recovery — if you run out of memory, the job dies. DuckDB can spill to disk but with performance penalty. Fix: monitor memory, use streaming/chunked reads for very large files, or upgrade to a bigger instance before reaching for Spark.

No fault tolerance: If the machine dies mid-job, you restart from scratch. Fine for 30-second jobs, unacceptable for 30-minute jobs. This is where the boundary with Spark lives — if single-node failure is costly, go distributed.

Before reaching for Spark, try DuckDB. It's embarrassingly fast for single-node analytics and has zero cluster overhead. A $2/hr EC2 instance running DuckDB can replace a $50/hr Spark cluster for most sub-100GB workloads.
DuckDB can query Parquet files directly in S3 without downloading them first: SELECT * FROM read_parquet('s3://bucket/data/*.parquet'). This is a game-changer for exploratory analytics.

Why push to warehouse

At >10TB, the cost of moving data out of the warehouse to process it in Spark exceeds the cost of just processing it in-place. BigQuery and Snowflake are optimized for exactly this: they separate compute from storage, auto-scale parallelism, and handle petabyte-scale joins natively. You pay for compute time, not cluster idle time.

Scale numbers

BigQuery 10TB scan + aggregation~30-90 seconds
BigQuery cost for 10TB scan~$50 on-demand
Snowflake 4XL same workload~2-5 min, ~$100-200
BigQuery flat-rate$2k/month for 100 slots
Data egress cost$0.12/GB — another reason to stay in-warehouse

External table loading

-- BigQuery: load Parquet from GCS as external table, then transform in-place CREATE OR REPLACE EXTERNAL TABLE raw.events OPTIONS ( format = 'PARQUET', uris = ['gs://bucket/events/*.parquet'] ); -- Transform and materialize CREATE OR REPLACE TABLE analytics.events_daily PARTITION BY event_date CLUSTER BY user_id AS SELECT DATE(event_timestamp) as event_date, user_id, event_type, COUNT(*) as event_count FROM raw.events GROUP BY 1, 2, 3;
If your batch job is expressible in SQL, don't use Spark. Warehouses are optimized for exactly this and require zero cluster management. The operational simplicity alone is worth the slightly higher per-query cost.
Watch out for on-demand pricing at scale. If you're scanning 10TB+ daily, switch to flat-rate/reserved pricing. BigQuery on-demand at 100TB/day = $500/day = $15k/month. Flat-rate at $2k/month is 7.5x cheaper.

CDC-based Batch Sync (Debezium / Fivetran)

Why CDC batch sync

Instead of full table dumps (slow, expensive, blocks the source DB), CDC reads the database's WAL/binlog to capture only changed rows. This is non-intrusive to the source DB, captures deletes (which query-based sync misses), and is much faster for large tables where only a small fraction changes per sync window.

Architecture options

Self-hosted: Debezium → Kafka → batch consumerhourly/daily warehouse loads
Managed: Fivetran / Airbyte150+ connectors, managed
Fivetran: 50M rows/day from Postgres~15 min sync window
Debezium latency to Kafkasub-second
Fivetran pricing$1-2/credit (per million rows)

Failure modes

WAL retention: If your CDC consumer falls behind and the database has rotated its WAL, you lose change events. Fix: set wal_keep_size high enough, monitor consumer lag, alert if lag exceeds retention window.

Schema drift: Source DB schema changes break the sync. A column rename or type change can cause silent data loss. Fix: schema registry, automated schema evolution detection, dbt tests on destination tables.

For most teams, Fivetran or Airbyte is the right choice over self-hosted Debezium. The operational overhead of running Debezium + Kafka + batch consumer is significant. Managed CDC lets you focus on the transforms, not the plumbing.

GPU
Critical for Anthropic interview
Offline LLM Batch Inference
Maximize GPU utilization for bulk model scoring at scale
GPU-bound continuous batching memory-bound KV cache vLLM / TGI

The challenge

LLM inference is fundamentally different from classical ML batch. Autoregressive generation means each token depends on all previous tokens — you can't parallelize within a single sequence. Memory scales with sequence length due to the KV cache (storing key/value pairs for attention). GPU utilization is typically 30-60% for naive static batching because shorter sequences pad to the longest sequence length, wasting compute.

Architecture

// High-level batch inference pipeline Input Store (S3/GCS) ↓ partitioned by estimated sequence length Job Queue (SQS / Redis) ↓ work items with priority + metadata Scheduler (continuous batching) ↓ packs requests into GPU memory dynamically GPU Worker Pool (vLLM / TGI / TensorRT-LLM) │ prefill: compute-bound (~10k tok/s on A100 for 70B) │ decode: memory-bandwidth-bound (~300-500 tok/s) ↓ Output Store (S3/GCS/database) ↓ checkpointed, idempotent writes Monitoring (tokens/s, GPU util, queue depth, error rate)

Scale numbers

70B model memory (FP16)~140 GB → 2x A100-80GB
70B model memory (INT4 quantized)~35 GB → 1x A100-80GB
Throughput (70B, A100, large batch)~100-500 tok/s per GPU
Prefill throughput (70B, A100)~10k tok/s (compute-bound)
Decode throughput (70B, A100)~300-500 tok/s (mem-BW bound)
10M docs x 200 tok output~2B tokens total
Time at 300 tok/s per GPU~77 GPU-hours
Cost (A100 spot ~$1.50/hr)~$115-230 total

Key optimizations — know these cold

Continuous batching: Don't block on the longest sequence. As sequences finish generating, immediately slot in new requests from the queue. This is the single biggest optimization — 2-4x throughput improvement over static batching. vLLM and TGI implement this natively.

PagedAttention (vLLM): Treats the KV cache like virtual memory. Instead of pre-allocating contiguous memory for max sequence length, it allocates in pages on demand. Eliminates internal fragmentation, allows much larger batch sizes. This alone can double throughput by fitting 2x more requests in GPU memory.

Quantization: INT8 reduces memory 2x with <0.5% quality loss for most tasks. INT4 (GPTQ, AWQ) reduces 4x with <1% quality loss. Fits 70B model on a single A100-80GB in INT4. Always benchmark quality on YOUR specific task — classification may be fine, creative writing may degrade.

Speculative decoding: A small "draft" model (7B) proposes N tokens, the main model (70B) verifies all N in a single forward pass. If the draft model guesses correctly (common for easy tokens), you get N tokens for the cost of 1 main model step. 2-3x speedup for greedy/low-temperature decoding.

Tensor parallelism: Split model layers across GPUs with NVLink. 70B on 4 GPUs = ~4x memory capacity but only ~2-3x throughput due to inter-GPU communication. Use pipeline parallelism (split layers) for batch inference to overlap compute and communication.

Failure modes — interview gold

OOM on long sequences: KV cache grows linearly with sequence length. A few 32k-token requests mixed with 1k-token requests can OOM the GPU. Fix: sequence length limits per request, dynamic batching that tracks available KV cache memory (vLLM does this), separate queues for long vs short sequences.

GPU idle during prefill: Prefill (processing the prompt) is compute-bound. If your batch has mixed prompt lengths, shorter prompts finish prefill and wait. Fix: sort requests by prompt length, use bucketed batching. In continuous batching, prefill of new requests interleaves with decode of existing ones — called "chunked prefill".

Checkpoint/restart: GPU spot instances get reclaimed (2-minute warning on AWS). NCCL timeouts crash multi-GPU jobs. Fix: checkpoint completed items to S3/GCS after each batch, make processing idempotent (store results keyed by input hash), resume from last checkpoint on restart.

Result poisoning: One malformed input (encoding error, adversarial prompt, extreme length) crashes the batch worker. Fix: input validation + sanitization before queuing, per-item try/catch in the worker, quarantine failed items to a dead-letter queue with the error for investigation.

Throughput cliff: Batch size too large causes KV cache to exceed GPU memory. Instead of OOM, some frameworks fall back to recomputation (recomputing KV pairs instead of caching them). This causes a 10x throughput drop with no visible error. Fix: monitor GPU memory utilization (not just compute utilization), set explicit max_num_seqs in vLLM, profile the memory-throughput curve for your specific model.

The single biggest mistake in LLM batch inference: treating it like classical ML batch. In classical ML, bigger batch = always better GPU utilization. In LLMs, batch size is constrained by KV cache memory, not compute. Going 1 item over the memory threshold can drop throughput by 10x due to recomputation fallback.
For Anthropic-scale inference: the system design question is really about scheduling. How do you maximize GPU utilization across thousands of heterogeneous requests with different prompt lengths, different output lengths, different priority levels? This is essentially a bin-packing problem with a time dimension. The scheduler must balance: (1) GPU memory for KV cache, (2) compute budget for prefill vs decode, (3) SLA deadlines, (4) cost (spot vs on-demand).
Always measure tokens/second/dollar, not just tokens/second. A 70B model on 2x A100 at 300 tok/s costs $3/hr = $0.0028 per 1k tokens. The same model quantized to INT4 on 1x A100 at 250 tok/s costs $1.50/hr = $0.0017 per 1k tokens — 40% cheaper even though raw throughput is lower.
path: ML/AI → LLM → offline bulk scoring
NRT
Recommended
Near-Realtime LLM Inference Pipeline
Minutes-latency LLM processing with auto-scaling GPU pool
minutes-latency GPU auto-scaling SLA-driven queue-based

When you need minutes, not hours

Content moderation within 5 min of posting. Document classification as they arrive. The key difference from offline bulk: you must right-size your GPU pool to meet an SLA, not just maximize throughput. Over-provisioning wastes expensive GPU time. Under-provisioning means SLA violations and growing queues.

Architecture

Kafka / SQS (input queue) ↓ partitioned by priority Auto-scaling GPU Pool (EKS / GKE + vLLM) │ scale trigger: queue_depth > threshold for > 2 min │ scale-down delay: 10 min (GPU startup is ~2-5 min) │ min replicas: enough for baseline traffic ↓ Result Topic / Table ↓ consumer reads results, updates downstream // Key metric: time_in_queue + inference_time < SLA // If queue_time dominates → need more GPU replicas // If inference_time dominates → need faster model/hardware

Scale numbers

Target end-to-end latencyp99 < 5 min
Cold start (model loading)30s-2 min for 70B model
Container pull + model load2-5 min total
GPU scale-up time3-7 min (instance + container + model)
Queue depth monitoring interval30 seconds

Failure modes

Cold start latency: Loading a 70B model into GPU memory takes 30s-2min. If you scale to zero and traffic arrives, the first request waits 5+ minutes. Fix: always keep minimum replicas warm, pre-pull container images to GPU nodes, use model caching on local NVMe.

Queue backup during spikes: Traffic 10x spikes (e.g., viral content needing moderation). GPU scaling is slow (minutes). Fix: pre-computed scale targets based on queue growth rate, not just depth. If queue is growing at 1000 items/min and you process 100/min/GPU, you need 10 more GPUs NOW, not when queue hits threshold.

Priority inversion: Low-priority bulk items fill the queue, high-priority items wait behind them. Fix: separate queues per priority, or priority-aware scheduling that preempts low-priority batches.

Scale on queue depth growth rate, not absolute depth. By the time queue depth hits a static threshold, you're already behind. Predictive scaling based on arrival rate vs processing rate catches spikes 5-10 minutes earlier.
Consider keeping a "warm pool" of GPU instances with models loaded but not actively processing. They cost money but eliminate cold start. For a 5-minute SLA, cold start of 3-5 minutes leaves almost no room for actual inference.

Why Spark for classical ML

For classical ML (XGBoost, LightGBM, sklearn), inference is CPU-bound and fast — the bottleneck is feature engineering, not prediction. Typical pattern: Spark for distributed feature engineering (joins, aggregations, window functions across TB of data), then broadcast the trained model to all executors for parallel prediction. Feature engineering is usually 80% of the total job time.

Scale numbers

XGBoost inference on 100M rows~5-10 min on 10 nodes
Feature engineering on 1TB~20-40 min on 20 nodes
sklearn predict (per node)~100k-1M predictions/s
Model broadcast overheadseconds (model is small, <1GB)

Pattern

# Typical Spark + sklearn batch inference import pyspark.sql.functions as F from pyspark.sql import SparkSession # 1. Feature engineering in Spark (the slow part) features_df = ( raw_events .groupBy("user_id") .agg( F.count("*").alias("event_count"), F.avg("session_duration").alias("avg_session"), F.countDistinct("page_id").alias("unique_pages") ) ) # 2. Broadcast model to all executors model_broadcast = spark.sparkContext.broadcast(trained_model) # 3. Predict with UDF (the fast part) @F.udf("double") def predict(features): return float(model_broadcast.value.predict([features])[0])
Consider using Spark's mapInPandas() or mapInArrow() instead of row-level UDFs. These process data in batches (Arrow RecordBatches), avoiding Python serialization overhead. 10-100x faster than row-level UDFs for sklearn/XGBoost inference.

EMB
Recommended
Batch Embedding Generation
Vectorize millions of documents for semantic search and RAG
GPU-accelerated vector output RAG / search model-versioned

Why batch embeddings

Semantic search, RAG pipelines, recommendation systems, and duplicate detection all require dense vector representations of text/images. Embedding models (sentence-transformers, OpenAI ada-002, Cohere) convert documents into fixed-size vectors. Unlike autoregressive LLMs, embedding models process the full input in a single forward pass — much simpler to batch and parallelize.

Architecture

Document Store (S3 / database) ↓ Chunking Pipeline (split docs into ~512 token chunks) ↓ GPU Embedding Workers (sentence-transformers / TGI) │ batch_size=256, process in parallel ↓ Vector DB (Pinecone / Weaviate / pgvector / Qdrant) │ store: (doc_id, chunk_id, vector, metadata, model_version) ↓ Search API (query → embed → ANN search → retrieve)

Scale numbers

sentence-transformers on A100~5k embeddings/s (384-dim)
10M documents self-hosted~30 min on A100
OpenAI API rate limit~3k/min → 10M docs = ~55 hours
OpenAI API cost (ada-002)~$1.30 per 1M tokens
Self-hosted GPU cost~$1.50/hr → $0.75 for 10M docs
Vector storage (1B x 384-dim float32)~1.5 TB raw

Critical failure mode: model version drift

If you update the embedding model (new version, different dimensions, fine-tuned weights), ALL existing vectors become incompatible. You cannot mix vectors from different model versions in the same index — cosine similarity between v1 and v2 embeddings is meaningless. Plan for full reindex: maintain a mapping of model_version → vector_index, and run the new embedding batch in parallel before switching the search API to the new index.

For RAG systems, embedding generation is the batch job that directly impacts retrieval quality. Always version your embedding model and maintain a mapping of model_version → vector_index. A model update means a full reindex — budget GPU time and cost accordingly.
Self-hosted embeddings are 50-100x cheaper than API-based for large batches. 10M documents via OpenAI API: ~55 hours + ~$500. Self-hosted on A100: ~30 minutes + ~$0.75. The API only makes sense for <100k documents or when you can't manage GPU infrastructure.

Why warehouse compute

If your batch computation is expressible in SQL (GROUP BY, JOIN, window functions, HAVING, CTEs), don't use Spark. Modern warehouses are optimized for exactly this: columnar storage, automatic parallelism, query optimization, and zero cluster management. BigQuery can scan 10TB and return results in under 90 seconds. Snowflake separates compute from storage so you pay for active time only.

Why graph processing

PageRank, connected components, shortest paths, community detection — these algorithms iterate over the full graph multiple times until convergence. Each vertex sends messages to neighbors, processes received messages, and updates its state. This is the Bulk Synchronous Parallel (BSP) model. SQL can't express this efficiently because each iteration depends on the previous one.

Scale numbers

PageRank on 1B edges (20 iterations)~30-60 min on 50 nodes
Connected components on 1B edges~20-40 min on 50 nodes
Memory per nodehigh — graph must fit in aggregate cluster memory
Communication overheadhigh — every iteration shuffles messages

Alternatives

Neo4j: Better for smaller graphs (<100M edges) with complex traversals and Cypher queries. Not distributed by default. Apache Giraph: Purpose-built for massive graph processing (Facebook scale). Better memory efficiency than GraphX but harder to operate. GraphFrames (Spark): DataFrame-based graph API, more ergonomic than GraphX, integrates with Spark SQL.

Most "graph problems" at interview scale don't actually need a graph engine. If you're computing 2-hop connections or simple aggregations over a graph structure, a SQL self-join in BigQuery is simpler and faster. Reserve GraphX/Pregel for truly iterative algorithms that need convergence.

UDF
Recommended
Spark Custom Per-Record Processing
Arbitrary transforms in Python/Scala distributed across a cluster
UDFs / mapPartitions distributed Python / Scala Arrow-optimized

When you need custom code

Image processing, NLP preprocessing, complex business logic, calling external APIs per record — anything that doesn't fit SQL. Spark distributes your custom code across the cluster, handling partitioning, fault tolerance, and scheduling. Use mapPartitions for heavy initialization (loading models, opening connections) — it runs once per partition instead of once per row.

Performance pitfall: Python UDF serialization

PySpark row-level UDFs serialize each row from JVM to Python and back. This serialization overhead can be 10-100x slower than native Spark SQL operations. The fix is Apache Arrow-based UDFs: pandas_udf or mapInArrow process entire batches in vectorized numpy/pandas operations. This eliminates per-row serialization and enables SIMD optimizations.

# SLOW: row-level UDF (serializes each row) @udf("string") def clean_text(text): return text.lower().strip() # FAST: Arrow-based batch UDF (10-100x faster) @pandas_udf("string") def clean_text_batch(texts: pd.Series) -> pd.Series: return texts.str.lower().str.strip()
Python UDF serialization is the #1 PySpark performance trap. A simple string transformation that takes 2 minutes in Spark SQL can take 2 hours with a row-level Python UDF. Always use pandas_udf or mapInArrow for batch processing.
For external API calls (geocoding, enrichment), use mapPartitions with connection pooling and rate limiting. Process in batches, not per-row. Implement exponential backoff and circuit breakers to avoid overwhelming external services.

Cron is fine for fewer than 5 jobs with no dependencies between them. A cron job that runs a Python script every hour is the simplest possible orchestration. Why a full orchestrator

When you have dozens of interdependent batch jobs across multiple teams, you need: dependency management (job B waits for job A), retry policies (exponential backoff, max retries), SLA monitoring (alert if job hasn't finished by 6am), backfill (reprocess last 30 days after a bug fix), audit logging (who ran what, when, with what result). Airflow and Dagster are the two leading options.

Apache Airflow

Mature (2015+). Huge community. 1000+ operators/providers. Can be painful to test locally. Task-centric model. Managed options: MWAA (AWS), Cloud Composer (GCP).

Dagster

Asset-centric (2019+). Better testing story. Software-defined assets model data lineage. Type checking. Better local development. Dagster Cloud for managed hosting.

Scale numbers

Airflow + CeleryExecutor capacity1000s of DAGs, 100k+ tasks/day
Airflow + KubernetesExecutoreach task = isolated pod, auto-scales

Failure modes — what breaks in production

Scheduler bottleneck: A single scheduler processes all DAG files. With >500 DAGs on 1-minute schedules, the scheduler falls behind — DAGs start late, tasks queue up. Fix: multiple schedulers (Airflow 2.x), increase min_file_process_interval, reduce DAG complexity (use TaskGroups instead of sprawling DAGs).

Worker OOM: A task runs on a Celery worker with insufficient memory. The worker dies, taking all its running tasks with it. Fix: use KubernetesPodOperator for memory-heavy tasks (each task gets isolated resources), set task-level resource requirements, monitor worker memory.

Zombie tasks: A task is marked "running" in the metadata DB, but the worker that was executing it has died. The task appears stuck. Fix: tune scheduler_zombie_task_threshold (default 300s), ensure heartbeat monitoring is working, implement health checks on workers.

Cross-DAG dependencies: DAG A produces data that DAG B consumes. Airflow has no native cross-DAG dependency model. ExternalTaskSensor polls for completion but creates tight coupling and can waste worker slots. Fix: use Dagster's asset-centric model (assets declare dependencies explicitly), or use a shared data catalog with freshness checks instead of sensor-based polling.

Airflow is an ORCHESTRATOR, not an EXECUTOR. Don't run heavy processing inside Airflow tasks — use Airflow to trigger Spark jobs (SparkSubmitOperator), dbt runs (DbtRunOperator), or Kubernetes pods (KubernetesPodOperator). Airflow workers should be lightweight coordinators.
If starting fresh in 2024+, strongly consider Dagster over Airflow. The asset-centric model (declaring "what data exists" rather than "what tasks run") maps better to how data teams actually think. It also solves the cross-DAG dependency problem natively. The main reason to choose Airflow is if your team already knows it or you need the massive ecosystem of community operators.

Why ML-specific orchestration

ML pipelines have unique requirements beyond general DAG orchestration: experiment tracking (compare hyperparameters across runs), model versioning (which model is in production?), automated evaluation (compare new model vs current champion on holdout set), model registry (artifact storage with metadata), and deployment automation (canary rollout, A/B testing, rollback). General orchestrators like Airflow can do this, but ML platforms bake these concepts in.

Kubeflow Pipelines

Kubernetes-native. Flexible. Complex to set up. Full control over infrastructure. Best for teams already on K8s with strong platform engineering.

SageMaker Pipelines

AWS-managed. Opinionated but simple. Built-in training, tuning, deployment. Best for AWS-heavy teams who want managed everything.

MLflow

Lightweight. Focus on experiment tracking + model registry. Works with any compute. Not a full orchestrator — pair with Airflow/Dagster for scheduling.

Ray + Anyscale

Distributed Python. Excellent for distributed training + inference. Ray Train, Ray Serve. Best for teams doing custom distributed ML at scale.

Key design pattern: Champion/Challenger

# Automated retraining pipeline Schedule: weekly (or on data drift detection) 1. Data prep → fresh training/eval split 2. Train challenger model → log to MLflow 3. Evaluate on holdout set ├─ if challenger > champion by threshold → promote └─ if not → log results, keep champion 4. Register new model version in registry 5. Deploy canary (5% traffic) 6. Monitor online metrics for 24h ├─ if degradation → auto-rollback └─ if stable → promote to 100%
The biggest risk in ML pipelines isn't model accuracy — it's silent degradation. A model deployed 6 months ago may have drifted as user behavior changed. Build automated monitoring for prediction distribution shifts, feature drift, and online metric degradation. Trigger retraining automatically, don't wait for someone to notice.

Golden rules
01Batch size isn't free — larger batches mean longer recovery time on failure. Checkpoint frequently.
02Idempotency is non-negotiable. Every batch job must produce the same output if run twice on the same input.
03Partition by time first, then by key. Time partitions enable efficient backfill and incremental processing.
04Monitor wall-clock time, not just throughput. A job processing 1M rec/s that takes 4 hours has a problem.
05Test with production-scale data, not 1% samples. Skew and OOM only appear at scale.
06Separate compute from storage. S3/GCS + Spark/warehouse is almost always better than HDFS.
07Plan for backfill from day one. You WILL need to reprocess historical data. Design for it.
08For GPU batch: measure tokens/second/dollar, not just tokens/second. Spot instances change the math.
