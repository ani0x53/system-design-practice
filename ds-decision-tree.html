Starting point
What operation do you need to be fast?
Every data structure is an answer to a specific performance problem. Pick the bottleneck you're actually hitting — the right structure follows from that.
Sequential access

Store items, access by position. Arrays, lists, stacks, queues — the building blocks of everything else.

Ordered search

Find, insert, delete while maintaining sorted order. BSTs, balanced trees, B-trees — the engine behind databases.

Priority access

Always grab the min or max first. Heaps and priority queues — used in scheduling, shortest-path, and stream processing.

Graph traversal

Find paths between connected nodes. BFS, DFS, Dijkstra — the foundation of routing, social graphs, and dependency resolution.

Sequential → step 1 of 2
What's your access pattern?
The core tradeoff: contiguous memory (fast reads, slow inserts) vs. linked nodes (fast inserts, slow reads). Pick based on what you do most.
1
Index-based random access, size known upfront
You know the size at creation time. Access by index is the hot path. No inserts in the middle.
arr[i] = O(1). Contiguous memory → CPU cache friendly.
2
Dynamic size, mostly append at the end
Size isn't known upfront. You add/remove elements mainly at the tail. Still need fast index access.
Amortized O(1) append. Doubles capacity when full. Still cache-friendly.
3
Frequent insert/delete at arbitrary positions
You insert or remove in the middle often, and you already have a reference to the node. Iteration order matters more than index access.
Insert/delete at known position = O(1). But finding the position = O(n).
4
Restricted access — only the top or front
You don't need arbitrary access. Elements go in one end and come out from one (or both) ends, in a strict order.
Stack (LIFO) or Queue (FIFO) — O(1) push/pop on both.
Sequential → restricted → step 2 of 2
What order do elements come out?
LIFO and FIFO seem simple, but they're the backbone of function calls, undo systems, task scheduling, and graph traversal.
1
Last in, first out — LIFO
Undo/redo, browser back button, function call stack, DFS, expression evaluation, matching parentheses.
Push and pop both O(1). Array-backed in practice (not linked list).
2
First in, first out — FIFO
Task scheduling, BFS, print queue, message queues, rate limiters, sliding window.
Enqueue and dequeue both O(1). Circular array or linked list backed.
Ordered search → step 1 of 2
How balanced must your search tree stay?
An unbalanced BST degrades to a linked list — O(n) search. The question is how much you're willing to pay for balance guarantees.
1
Data is roughly random — simple BST is fine
Insertions come in random order. Worst-case isn't a concern. You want the simplest implementation.
Average O(log n) search/insert. Worst case O(n) if sorted input.
2
Must guarantee O(log n) worst case, in-memory
Adversarial or sorted input is possible. You need guaranteed logarithmic operations. TreeMap, TreeSet — all self-balancing BSTs.
Red-Black: max height 2·log₂(n). AVL: stricter — max height 1.44·log₂(n).
3
Massive dataset — minimize disk I/O
Data doesn't fit in RAM. You need to minimize disk reads. Each node should hold many keys to reduce tree height.
B-Tree with order 1000: 1 billion keys in ~3 levels = 3 disk reads.
Priority → step 1 of 2
Do you need to update priorities of existing items?
A basic heap is great for extract-min/max. But some algorithms (Dijkstra, Prim's) need to decrease the priority of an item already in the heap — that changes which implementation you need.
1
No — just insert and extract-min/max
Process events by timestamp, merge k sorted lists, find the k largest elements, median maintenance.
Insert: O(log n). Extract-min: O(log n). Peek: O(1). Array-backed, no pointers.
2
Yes — need to decrease-key for existing entries
Running Dijkstra's algorithm, Prim's MST, or any algorithm that discovers a shorter path to a node already in the queue.
Binary heap decrease-key: O(log n). Fibonacci heap: O(1) amortized.
Graph traversal → step 1 of 2
What kind of path are you looking for?
BFS finds shortest paths in unweighted graphs. DFS explores exhaustively. Dijkstra handles weighted edges. The right algorithm depends on what "shortest" means in your graph.
1
Shortest path — all edges have equal weight
Social network "degrees of separation", word ladder, maze shortest path, web crawler level-by-level.
O(V + E) time. Uses a Queue. Guarantees shortest path in unweighted graphs.
2
Explore all paths, detect cycles, topological sort
Course prerequisite ordering, dependency resolution, cycle detection, maze generation, connected components.
O(V + E) time. Uses a Stack (or recursion). Memory-efficient: O(V) vs BFS O(V).
3
Shortest path — edges have different weights
GPS navigation, network routing (OSPF), cheapest flight, minimum latency path.
O((V + E) log V) with a min-heap. No negative edge weights.
[]
Recommended structure
Array
Contiguous memory. O(1) index access. The simplest and fastest sequential structure.
O(1) read by index cache-friendly zero overhead per element fixed size at creation O(n) insert in middle

Why it works

Elements are stored in contiguous memory. The address of element i is just base + i × element_size — pure arithmetic, no pointer chasing. This also means the CPU prefetcher can predict your access pattern and preload cache lines. For sequential scans, arrays are unbeatable.

Time complexity

Access by indexO(1)
Search (unsorted)O(n)
Search (sorted)O(log n) — binary search
Insert at end (if space)O(1)
Insert at index iO(n) — shift everything right
Delete at index iO(n) — shift everything left

Memory layout

// Contiguous block in memory ┌─────┬─────┬─────┬─────┬─────┐ │ 3 │ 7 │ 1 │ 9 │ 4 │ └─────┴─────┴─────┴─────┴─────┘ [0] [1] [2] [3] [4] addr[i] = base + i × sizeof(element) // One multiplication. No pointers. No indirection.
In system design: arrays underpin everything. Hash table buckets, ring buffers, heap storage, adjacency matrices. When you hear "contiguous memory" in an interview, think array.
The fixed-size problem: if you guess too small, you can't grow. If you guess too big, you waste memory. This is exactly the problem that ArrayList/dynamic arrays solve.
AL
Recommended structure
ArrayList (Dynamic Array)
Array that grows automatically. Amortized O(1) append. The default list in most languages.
O(1) index access amortized O(1) append cache-friendly occasional O(n) resize O(n) insert in middle

Why it works

Starts with a small array. When full, allocates a new array 2× the size and copies everything over. The copy is O(n), but it happens so rarely that averaged over all operations, each append is O(1). This is the "amortized" trick — you pay for one expensive resize across many cheap appends.

Time complexity

Append (amortized)O(1)
Append (worst case — resize)O(n)
Insert at index iO(n)
Delete at index iO(n)
SearchO(n)

This is the default choice for any "list of things" in nearly every language. Unless you have a specific reason to use something else, use this. Java's ArrayList, Python's list, Go's slice, C++ std::vector are all dynamic arrays.
If you're inserting millions of items at arbitrary positions (not the end), this is the wrong structure. Each mid-insert shifts O(n) elements. Consider a linked list or a balanced BST for that pattern.
LL
Recommended structure
Linked List
O(1) insert/delete at a known position. No shifting. No resizing. But no random access.
O(1) insert/delete at known node no capacity limits stable pointers (no invalidation) O(n) access by index poor cache locality extra pointer overhead per node

Why it works (and when it doesn't)

Each node stores data + a pointer to the next node (and previous, for doubly-linked). Insert/delete is just pointer rewiring — O(1) if you already have the node reference. The catch: to find a node by index, you must walk from the head — O(n). Nodes are scattered in memory, so the CPU cache can't help you. In practice, ArrayList beats LinkedList for almost everything due to cache effects, unless you have a workload dominated by mid-list insert/delete with direct node references (e.g., LRU cache).

Time complexity

Access by indexO(n)
Insert/delete at headO(1)
Insert/delete at known nodeO(1)
SearchO(n)
Memory overhead (doubly-linked)+16 bytes/node (two pointers)

Singly vs Doubly linked

Singly linked

One pointer per node (next). Can only traverse forward. Less memory. Deletion requires reference to the previous node. Good for stacks, simple iteration.

Doubly linked

Two pointers per node (next + prev). Traverse both ways. O(1) deletion with just the node reference. Used in LRU caches, browser history, undo buffers.

Structure

// Singly linked ┌───┬───┐ ┌───┬───┐ ┌───┬───┐ ┌───┬───┐ │ 3 │ ──┼──→│ 7 │ ──┼──→│ 1 │ ──┼──→│ 9 │ ∅ │ └───┴───┘ └───┴───┘ └───┴───┘ └───┴───┘ head tail // Doubly linked ┌───┬───┬───┐ ┌───┬───┬───┐ ┌───┬───┬───┐ ∅ ←──┤ ← │ 3 │ → ├──→│ ← │ 7 │ → ├──→│ ← │ 1 │ → ├──→ ∅ └───┴───┴───┘ └───┴───┴───┘ └───┴───┴───┘ // Insert node X after node B: just rewire pointers // X.next = B.next; B.next.prev = X; B.next = X; X.prev = B;
The killer use case: LRU cache = HashMap + Doubly-Linked List. The map gives O(1) lookup, the linked list gives O(1) eviction and move-to-front. This is literally how every in-memory cache works (Memcached, Redis internals, OS page cache).
Bjarne Stroustrup (C++ creator) ran benchmarks: inserting in the middle of a std::vector is faster than std::list for lists up to ~500K elements, because cache locality dominates. Don't reach for linked lists by default — profile first.
ST
Recommended structure
Stack (LIFO)
Last in, first out. Push and pop in O(1). The data structure behind recursion itself.
O(1) push O(1) pop O(1) peek array-backed in practice no random access

Why it matters

Every function call in every program uses a stack (the call stack). When function A calls function B, A's state is pushed. When B returns, A's state is popped. Stacks also power DFS, expression evaluation, undo systems, and backtracking algorithms. The LIFO discipline means the most recent context is always what you work with.

Time complexity

Push (add to top)O(1)
Pop (remove from top)O(1)
Peek (view top)O(1)
SearchO(n)

Classic applications

// 1. Balanced parentheses: push open, pop on close, check match input: ( [ { } ] ) stack: ( → ( [ → ( [ { → ( [ → ( → ∅ ✓ // 2. DFS traversal: push neighbors, pop to visit push(start) while stack not empty: node = pop() for neighbor in node.neighbors: if not visited: push(neighbor) // 3. Undo system: each action pushed, Ctrl+Z pops do(action) → push(action) undo() → pop() and reverse it
In system design: the call stack is limited (~1MB default on most OSes, ~8MB on Linux). Deep recursion (100k+ frames) causes stack overflow. Convert to an explicit stack (heap-allocated) for deep traversals. This is why iterative DFS is preferred over recursive DFS in production code.
Q
Recommended structure
Queue (FIFO)
First in, first out. Fair ordering. The backbone of BFS, scheduling, and message passing.
O(1) enqueue O(1) dequeue O(1) peek circular array or linked list backed no random access

Why it matters

Queues enforce fairness — whoever arrives first gets served first. BFS uses a queue to explore nodes level-by-level, which is why it finds shortest paths in unweighted graphs. In system design, message queues (SQS, RabbitMQ) are just distributed queues. Thread pools, task schedulers, and print spoolers are all queues.

Time complexity

Enqueue (add to back)O(1)
Dequeue (remove from front)O(1)
Peek (view front)O(1)
SearchO(n)

Implementation: circular array

Queue → BFS → shortest path in unweighted graphs. Stack → DFS → topological sort, cycle detection. The data structure determines the algorithm. This is the single most important connection in CS 61B.
Deque (double-ended queue) gives you O(1) operations at both ends. Java's ArrayDeque is faster than both Stack and LinkedList for both stack and queue use cases. In practice, always use ArrayDeque.
BST
Recommended structure
Binary Search Tree
Ordered data with O(log n) average-case search, insert, delete. The foundation of all tree-based structures.
O(log n) average search O(log n) average insert in-order traversal = sorted O(n) worst case (degenerate) no balance guarantee

The invariant

For every node: all keys in the left subtree are smaller, all keys in the right subtree are larger. This single rule gives you O(log n) search — at each node, you eliminate half the remaining tree. In-order traversal (left → root → right) visits nodes in sorted order, which is why BSTs power ordered maps and sets.

Time complexity

Search (average, balanced)O(log n)
Search (worst, degenerate)O(n)
Insert (average)O(log n)
Delete (average)O(log n)
In-order traversalO(n) — visits every node once
Find min/maxO(log n) — leftmost/rightmost

The degenerate case

// Balanced BST (random insertion order) 8 / \ 4 12 / \ / \ 2 6 10 14 height = O(log n) // Degenerate BST (sorted insertion: 2,4,6,8,10) 2 \ 4 \ 6 height = O(n) \ literally a linked list 8 \ 10
If you insert sorted data into a plain BST, you get a linked list with O(n) operations. This is why balanced BSTs (Red-Black, AVL) exist. If your data could arrive in any order — including sorted — you need a self-balancing tree.
BST deletion has three cases: (1) leaf — just remove, (2) one child — replace with child, (3) two children — replace with in-order successor (leftmost node in right subtree), then delete that successor. Case 3 is the tricky interview question.
RB
Recommended structure
Red-Black Tree
Self-balancing BST. Guaranteed O(log n) everything. The tree behind TreeMap, TreeSet, and the Linux scheduler.
O(log n) guaranteed search O(log n) guaranteed insert O(log n) guaranteed delete complex implementation max height: 2·log₂(n+1)

The five rules

1. Every node is red or black. 2. The root is black. 3. Every null leaf is black. 4. Red nodes can't have red children (no red-red). 5. Every path from root to null leaf has the same number of black nodes (black-height). These five rules guarantee the tree height stays ≤ 2·log₂(n+1), which means O(log n) worst-case for everything.

Time complexity

SearchO(log n) guaranteed
InsertO(log n) + max 2 rotations
DeleteO(log n) + max 3 rotations
Space+1 bit per node (color)

Red-Black vs AVL

Red-Black Tree

Looser balance: height ≤ 2·log₂(n). Fewer rotations on insert/delete (max 2-3). Faster writes. Used in: Java TreeMap, C++ std::map, Linux CFS scheduler.

AVL Tree

Stricter balance: height ≤ 1.44·log₂(n). More rotations to maintain balance. Faster reads (shorter tree). Used in: databases, memory-constrained lookup tables.

Rotation intuition

// Left rotation at node X (X becomes left child of Y) X Y / \ → / \ a Y X c / \ / \ b c a b // Right rotation is the mirror. These are the only two // operations needed to rebalance any BST. // Insert: walk down, color red, fix violations going up. // At most 2 rotations to fix after insert.
You almost never implement a Red-Black tree yourself. Java's TreeMap/TreeSet, C++'s std::map/std::set, and Python's sortedcontainers all use self-balancing BSTs internally. Know the guarantees — O(log n) everything, ordered iteration — not the rotation cases.
The Left-Leaning Red-Black tree (LLRB), from Sedgewick, simplifies implementation to ~40 lines of code by adding one extra invariant: red links lean left. This is what CS 61B teaches. Same O(log n) guarantees with much less case analysis.
BT
Recommended structure
B-Tree
Wide, shallow, disk-optimised. Every database index is a B-Tree. 1 billion keys in 3 disk reads.
O(log n) search, insert, delete minimises disk I/O every database uses this node = 1 disk page (4–16KB) more complex than binary trees

Why not a binary tree on disk?

A binary tree with 1 billion nodes has height ~30. Each node is one disk read. That's 30 disk reads per lookup — at 10ms per HDD seek, that's 300ms. Unacceptable. A B-Tree with order 1000 stores ~1000 keys per node. Height is log₁₀₀₀(1B) ≈ 3. Three disk reads instead of thirty. Each node fits in one disk page (4–16KB), so you read it in a single I/O operation.

Time complexity

SearchO(log_b n) — b = branching factor
InsertO(log_b n) + possible split
DeleteO(log_b n) + possible merge
Disk reads per operation= tree height (typically 3–4)
Range scanB+Tree: sequential leaf scan

B-Tree vs B+Tree

B-Tree

Keys + data in both internal and leaf nodes. Slightly faster point lookups if the key is found early (internal node). Less common in practice.

B+Tree (databases use this)

Data only in leaf nodes. Internal nodes are pure index. Leaves are linked for fast range scans. More keys per internal node = shallower tree. This is what Postgres, MySQL, and SQLite actually use.

Structure

// B+Tree with order 4 (max 3 keys per node) ┌──────────────┐ │ 10 │ 20 │ internal node └──┬──────┬────┘ (keys only, no data) / | \ ┌────────┐ ┌──────────┐ ┌──────────────┐ │ 1,3,7 │→ │ 10,14,18 │→ │ 20, 25, 30 │ leaf nodes └────────┘ └──────────┘ └──────────────┘ (keys + data) linked → // Range query "WHERE x BETWEEN 7 AND 18": // 1. Binary search internal nodes → find leaf with 7 // 2. Scan right through linked leaves until 18 // Sequential I/O — fast even on spinning disks.
When someone says "add an index" in a database interview, they mean "build a B+Tree on that column." The index maps column values to row pointers. CREATE INDEX is literally "construct a B+Tree." Understanding this makes database performance intuition click.
LSM-Trees (Log-Structured Merge Trees) are the write-optimised alternative. Instead of updating the B-Tree in place, writes go to an in-memory buffer, then flush as sorted runs. Used by Cassandra, RocksDB, LevelDB. Trade read speed for write speed.
HP
Recommended structure
Binary Heap
O(1) peek at min/max. O(log n) insert and extract. Array-backed — no pointers, no overhead.
O(1) find-min/max O(log n) insert O(log n) extract-min/max array-backed, cache-friendly O(n) search for arbitrary element not sorted — only min/max guaranteed

Why it works

A binary heap is a complete binary tree stored in an array. The heap property: every parent ≤ its children (min-heap) or ≥ its children (max-heap). The root is always the min (or max). Insert at the end and "bubble up." Extract-min by swapping root with last element, then "sink down." Both operations follow one path from root to leaf — O(log n).

Time complexity

Peek min/maxO(1) — it's always the root
InsertO(log n) — bubble up
Extract min/maxO(log n) — sink down
Build heap from arrayO(n) — not O(n log n)!
Search arbitrary elementO(n) — no ordering beyond parent-child

Array representation

// Min-heap as a tree: 1 / \ 3 5 / \ / 7 4 8 // Same heap as an array (level-order): index: [0] [1] [2] [3] [4] [5] value: 1 3 5 7 4 8 // Navigation by arithmetic — no pointers needed: parent(i) = (i - 1) / 2 leftChild(i) = 2i + 1 rightChild(i) = 2i + 2 // Insert 2: place at end [6], bubble up // [6]→parent[2]=5 → swap → [2]→parent[0]=1 → stop
Heapify (build a heap from an unordered array) is O(n), not O(n log n). The insight: leaves (half the nodes) need zero work. Nodes at height h need O(h) work. The sum converges to O(n). This is a common interview trick question.
Classic applications: (1) Find the k-th largest element — O(n) with quickselect or O(n log k) with a min-heap of size k. (2) Merge k sorted lists — O(n log k) using a min-heap. (3) Median maintenance — one max-heap for lower half, one min-heap for upper half.
PQ
Recommended structure
Priority Queue with decrease-key
Binary heap + index map for O(log n) decrease-key. The engine inside Dijkstra and Prim's MST.
O(log n) insert O(log n) extract-min O(log n) decrease-key indexed binary heap Fibonacci heap: O(1) amortized decrease-key

Why decrease-key matters

In Dijkstra's algorithm, you discover shorter paths to nodes already in the queue. You need to update their priority without removing and reinserting. A plain binary heap can't find an arbitrary element efficiently. An indexed priority queue adds a HashMap from element → heap index, giving you O(log n) decrease-key.

Implementation comparison

Binary heap — insertO(log n)
Binary heap — extract-minO(log n)
Binary heap — decrease-keyO(n) search + O(log n) bubble
Indexed binary heap — decrease-keyO(log n) via index map
Fibonacci heap — decrease-keyO(1) amortized
Fibonacci heap — extract-minO(log n) amortized

Dijkstra's inner loop

// Dijkstra = BFS + Priority Queue // Instead of a FIFO queue, use a min-heap keyed by distance dist[start] = 0 pq.insert(start, 0) while pq not empty: u = pq.extractMin() for (v, weight) in neighbors(u): if dist[u] + weight < dist[v]: dist[v] = dist[u] + weight pq.decreaseKey(v, dist[v]) // ← this is why we need it // Without decrease-key: insert duplicate entries, // skip stale ones when extracted. Lazy approach — works // but uses more memory: O(E) heap size vs O(V).
In practice, most implementations use the "lazy" approach: insert a new (distance, node) pair instead of decreasing the key. When you extract a node with a stale distance, just skip it. This avoids the need for an indexed heap and is simpler to implement. Dijkstra still runs in O((V+E) log V) either way.
Fibonacci heaps have better theoretical complexity (O(1) decrease-key) but terrible constant factors and cache behaviour. In practice, a binary heap with the lazy approach beats Fibonacci heaps for all but astronomically large graphs. Theory ≠ practice.
BFS
Recommended algorithm
Breadth-First Search
Explore level by level. Shortest path in unweighted graphs. Uses a Queue.
O(V + E) time shortest path (unweighted) uses a Queue (FIFO) O(V) memory — stores entire frontier

Why it finds shortest paths

BFS visits all nodes at distance d before any node at distance d+1. This level-by-level expansion guarantees that the first time you reach a node, you've found the shortest path to it (in an unweighted graph). The Queue enforces this order — nodes discovered first are explored first (FIFO).

Complexity

TimeO(V + E)
Space (queue + visited)O(V)
Shortest path guaranteeYes (unweighted only)
Works on disconnected graphs?Only finds component containing start

Algorithm

function bfs(graph, start): queue = [start] visited = {start} dist = {start: 0} while queue not empty: node = queue.dequeue() // FIFO — process oldest first for neighbor in graph[node]: if neighbor not in visited: visited.add(neighbor) dist[neighbor] = dist[node] + 1 queue.enqueue(neighbor) return dist // Traversal order (level by level): // A Level 0: A // / \ Level 1: B, C // B C Level 2: D, E, F // /| \ // D E F
System design applications: (1) Social network "people you may know" — BFS from a user, friends-of-friends at distance 2. (2) Web crawler — BFS ensures you index pages closest to seed URLs first. (3) Network broadcast — packets propagate BFS-style through a network.
BFS stores the entire frontier (all nodes at the current distance) in memory. For graphs where the frontier grows exponentially (e.g., branching factor 50, depth 6 = 15 billion nodes), BFS runs out of memory. Consider bidirectional BFS or iterative deepening DFS.
DFS
Recommended algorithm
Depth-First Search
Go deep, then backtrack. Topological sort, cycle detection, connected components. Uses a Stack.
O(V + E) time O(V) space (stack depth) uses a Stack (LIFO) or recursion does NOT find shortest paths topological sort, cycle detection

Why DFS over BFS?

DFS explores one path to its end before backtracking. This makes it natural for: (1) topological sort — post-order gives reverse topo order, (2) cycle detection — a back edge to a node on the current path means a cycle, (3) connected components — one DFS from each unvisited node, (4) maze generation — random DFS creates interesting mazes. DFS also uses less memory when the graph is deep but narrow.

Algorithm & topological sort

DFS is the backbone of compiler design. Dependency resolution in build systems (Make, Gradle), package managers (npm, pip), and import analysis all use topological sort via DFS. If there's a cycle in dependencies, DFS detects it during traversal.
Recursive DFS on deep graphs can blow the call stack (StackOverflowError). The default JVM stack is ~512KB (~10K–20K frames). For graphs with diameter > 10K, use iterative DFS with an explicit stack on the heap.

Recommended algorithm
Dijkstra's Algorithm
Shortest path in weighted graphs. BFS + priority queue. The algorithm behind every GPS and network router.
O((V + E) log V) with min-heap optimal for non-negative weights uses Priority Queue no negative edge weights greedy — processes closest node first

The key insight

Dijkstra is just BFS where the queue is a priority queue keyed by distance. BFS processes nodes in FIFO order (all distance-1 before distance-2). Dijkstra processes nodes in order of their current shortest known distance. The greedy choice works because with non-negative weights, once you process a node, no shorter path to it can exist.

Algorithm

function dijkstra(graph, start): dist = {v: ∞ for v in graph} dist[start] = 0 pq = MinHeap() pq.insert(start, 0) while pq not empty: (u, d) = pq.extractMin() if d > dist[u]: continue // stale entry, skip for (v, weight) in graph[u]: newDist = dist[u] + weight if newDist < dist[v]: dist[v] = newDist pq.insert(v, newDist) // lazy: insert, don't decrease-key return dist // Example: A→B(4), A→C(1), C→B(2) // Process A: dist[B]=4, dist[C]=1 // Process C (closest): dist[B]=min(4, 1+2)=3 ← relaxation // Process B: done. Shortest A→B = 3 (via C)

The evolution: Queue → Stack → Priority Queue

// The data structure IS the algorithm: BFS + Queue = shortest path (unweighted) DFS + Stack = topological sort, cycle detection Dijkstra + Priority Queue = shortest path (weighted) // Same traversal skeleton, different frontier ordering. // This is the deepest insight from CS 61B.
Google Maps doesn't run vanilla Dijkstra. It uses A* (Dijkstra + heuristic) and contraction hierarchies (precomputed shortcuts). But the core is still Dijkstra's relaxation: "if I found a shorter path to you through me, update your distance." Every routing algorithm builds on this.
Why no negative weights? Dijkstra's greedy choice assumes once a node is processed, its distance is final. A negative edge could create a shorter path through an already-processed node, breaking this invariant. For negative weights (but no negative cycles), use Bellman-Ford in O(VE).

CS 61B golden rules
01ArrayList beats LinkedList in practice for almost everything. Cache locality > theoretical complexity.
02The data structure determines the algorithm: Queue→BFS, Stack→DFS, PQ→Dijkstra.
03Hash tables give O(1) average but no ordering. Trees give O(log n) with ordering. Know when you need order.
04B-Trees exist because RAM is fast and disk is slow. Every "CREATE INDEX" is a B+Tree.
05Amortized ≠ worst case. ArrayList append is O(1) amortized but O(n) worst case. Know the difference for real-time systems.
06Every self-balancing BST (Red-Black, AVL, 2-3) is O(log n) everything. Pick by write/read ratio, not by name.
07Dijkstra fails with negative edges. Bellman-Ford handles negatives. Floyd-Warshall handles all-pairs. Match algorithm to constraint.
