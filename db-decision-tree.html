Starting point
What is your primary bottleneck?
Be honest about what's actually slow before choosing a solution. The wrong diagnosis is the most common scaling mistake.
Signs of a read problem

SELECT queries are slow. Dashboard pages take 2–5s. DB CPU is high during peak reads. Query log shows repeated identical SELECTs.

Signs of a write problem

INSERT/UPDATE latency climbing. WAL disk usage grows. Replication lag increasing. DB write queue backing up. Application 504s on form submits.

Read optimisation → step 1 of 2
What kind of reads are bottlenecked?
The read pattern determines the solution. Key lookups, relational queries, analytics, and search each have completely different optimal tools.
1
Key lookups — fetch by ID, no JOINs
SELECT * FROM users WHERE id = ?. Session lookups, profile fetches, product by SKU, config values.
Postgres handles ~50k/s. Redis handles ~500k/s. DynamoDB handles millions/s.
2
Relational — JOINs, filters, aggregations
Multi-table JOINs, WHERE across columns, ORDER BY, pagination. Requires SQL semantics.
Postgres JOIN on indexed FK: ~15k/s. Complex JOIN: ~2–5k/s.
3
Analytics — GROUP BY, SUM, COUNT over millions of rows
Dashboards, reports, time-series aggregations, funnel analysis. Full table scans.
Postgres: <1k analytical queries/s. ClickHouse: 10B rows in <1s.
4
Full-text / fuzzy / relevance-ranked search
Autocomplete, "search for products named X", typo tolerance, relevance scoring.
Postgres FTS: ~500/s. Elasticsearch: ~10k searches/s with ranking.
Read → key lookups → step 2 of 2
Volume and data freshness requirements?
Key lookups scale very differently depending on read volume and how stale the data can be.
1
Under 50k reads/s, stale data OK for seconds
User profiles, product catalogue, config values, content that changes rarely. Cache hit rate matters most.
Redis at 1ms p99. 99% cache hit rate → DB sees ~500 req/s not 50k.
2
50k–500k reads/s, frequent updates, cache TTLs impractical
Real-time counters, live game state, inventory levels, presence indicators — data changes every second.
Redis dedicated cluster: 500k ops/s per node. Sub-millisecond at any scale.
3
500k+ reads/s, or need <10ms globally
Massive key-value at global scale. Sessions, leaderboards, IoT device state, feature flags at enterprise scale.
DynamoDB: unlimited horizontal scale. ~1–3ms read globally via DAX.
Read → relational → step 2 of 2
Read volume and query complexity?
Relational reads scale horizontally with read replicas up to a point. After that, caching and query optimisation matter more than more replicas.
1
Under 5k complex reads/s
Single replica handles this. Most early-stage apps. Check your EXPLAIN ANALYZE first — you likely have a missing index.
1 replica = 2–4× read capacity. Check slow query log for queries >100ms first.
2
5k–50k relational reads/s
Multiple replicas + Redis cache for hot paths. Route reads round-robin. Most mid-scale apps.
3 replicas + 90% cache hit rate = effectively unlimited relational reads for most apps.
3
50k+ relational reads/s, or giant tables
Table-level locks from VACUUM start hurting. Query planner degrades on very large tables. Time to shard or partition.
Postgres query planner degrades past ~500M rows per table. Declarative partitioning helps.
Read → analytics → step 2 of 2
Real-time or batch analytics?
Never run analytical queries on your OLTP primary — they lock rows and kill transactional performance. The question is which separate store to add.
1
Real-time dashboards, sub-second response on billions of rows
Live operational analytics, event counting, cohort analysis, product dashboards.
ClickHouse: 1B row COUNT in ~0.1s. Ingests 100k+ rows/s. 10× compression vs Postgres.
2
Batch — hourly or daily, BI tools, historical reports
ETL pipelines, Looker/Tableau, executive dashboards, monthly rollups. Query latency of seconds/minutes acceptable.
BigQuery: $5/TB queried. Redshift: best for sustained heavy BI. Snowflake: best for data sharing.
Write optimisation → step 1 of 3
Is the write load sustained or bursty?
This is the first fork. Bursty and sustained loads have completely different solutions. Confusing them leads to over-engineering.
1
Bursty — 10× normal load for minutes, then quiet
Lunch rush on a food app. Ticket sales going live. Game event start. Batch imports. Traffic spikes predictably then drops.
A Kafka topic absorbs spikes instantly. Consumer drains at DB's max speed (~5k writes/s).
2
Sustained — high write volume all the time
IoT telemetry, financial transactions, event streaming, user activity logging at scale.
Sustained >5k writes/s starts stressing a single Postgres node. >20k/s requires architectural change.
Write → sustained → step 2 of 3
Do you need relational integrity on this data?
SQL and ACID transactions are powerful but limit write scalability. If you genuinely need them, you shard. If you don't, purpose-built stores are faster and cheaper.
1
Yes — need SQL, JOINs, and ACID
Orders and order_items must be consistent. Inventory must not go negative. Financial double-entry bookkeeping.
Every ACID guarantee has a throughput cost. Cross-row transactions add ~2–5ms overhead.
2
No — append-only, key-based, or eventual consistency OK
Event logs, sensor data, activity streams, user actions. Each write is independent. No cross-row transactions needed.
Without ACID overhead: Cassandra handles 1M+ writes/s on a modest cluster.
Write → sustained → relational → step 3 of 3
Sustained writes per second?
1
Under 10k writes/s
Postgres handles this with batching and a write queue. No schema change needed.
Batch 100 rows per INSERT → ~20k rows/s. Single inserts → ~5k/s.
2
10k–100k writes/s
Need to shard. Citus splits Postgres across nodes automatically on a distribution column.
8 Citus shards × 10k writes/s = 80k aggregate writes/s. Linear scaling.
3
100k+ writes/s, still need SQL
Aggressive sharding with Citus, or consider CockroachDB / YugabyteDB for distributed SQL.
CockroachDB: distributed SQL, auto-rebalancing. ~10–50k writes/s per node, scales horizontally.
Write → sustained → key-based → step 3 of 3
What is the shape of the data?
The data shape determines which write-optimised store fits best. Each is built around a specific access pattern.
1
Wide rows — one entity, many time-ordered events
user_id → all their messages. device_id → all sensor readings. conversation_id → all chat events.
Cassandra/ScyllaDB: 1M+ writes/s on a 10-node cluster. p99 write latency ~1ms.
2
Flat key-value — one document per partition key
Session store, player game state, order status, feature flags, real-time leaderboard entries.
DynamoDB: unlimited WCU. ~1–3ms write globally. ~$1.25 per million writes.
3
Time-series — numeric metrics, monotonic timestamps
CPU/memory metrics, stock prices, IoT sensor readings, request latency percentiles.
TimescaleDB: 500k+ rows/s ingest. InfluxDB: 1M+ data points/s. 10–50× compression vs Postgres.
Mixed workload → step 1 of 1
What best describes your data access pattern?
Mixed workloads are often solved by separating concerns — one store for writes, a different one (or model) for reads.
1
Relational — JOINs, SQL, ACID transactions
Standard web app. Users, posts, orders, inventory. Rich queries on writes AND reads.
The full Postgres stack handles hundreds of thousands of ops/s before you need to change the DB.
2
Key-based — no JOINs, simple fetch and store
Gaming, real-time bidding, live counters, presence tracking. Both reads and writes are key-based.
DynamoDB handles both at any scale. DAX cache layer for hot reads: <1ms.
3
Asymmetric — writes are appends, reads are complex
Event sourcing. Writes are fast appends. Read queries are expensive projections over the event log.
CQRS: writes to Kafka/event store (~1M/s), read models built asynchronously (Elasticsearch, Redis, Postgres).
PG
Recommended solution
Redis + Postgres read replica
Solve in a day. Handle 500k+ reads/s on cached paths.
keep full SQL no migration cache hit rate = free scale cache invalidation needed replication lag: 10ms–2s

What to build

Add Redis in front of your hot read paths. Set TTLs on all keys. Route all SELECT queries to a Postgres read replica; writes stay on primary. pgBouncer for connection pooling. This stack is often enough to 10–100× your read capacity in 1–2 days with zero schema changes.

Real numbers

Redis single node reads/s~500k ops/s
Redis p99 latency (LAN)<0.5ms
Postgres read replica reads/s~50k simple, ~5k complex
Memory per 1M cached objects (avg 1KB)~1GB RAM
pgBouncer: raw connections → virtual100 → 10,000
Replication lag (async, light load)~10–50ms
Replication lag (async, heavy load)100ms–2s
Cache stampede: when a hot key expires, all concurrent requests miss and hammer the DB simultaneously. Fix with probabilistic early expiry or a distributed lock (one fetches, others wait). Add jitter to TTLs: TTL + random(0, 30s).
Read-your-own-writes pattern: after a user writes data, store their write timestamp in session. Route their reads to primary for 5–10s. Prevents "I just posted a review but it disappeared" confusion caused by replica lag.

What to build

Redis Cluster with 3+ primary nodes + replicas. Use Redis data structures — Hash for objects, Sorted Set for leaderboards, HyperLogLog for cardinality, Pub/Sub for events. Persist with RDB snapshots + AOF. Keep Postgres as the durable record of truth for anything that needs SQL; Redis holds the hot operational state.

Real numbers

Single Redis node ops/s~500k–1M ops/s
Redis Cluster (6 nodes)~3–5M ops/s aggregate
p99 latency (LAN)<1ms
Memory per million small objects~100MB–2GB depending on type
Cost of 64GB Redis node (AWS)~$300/month (ElastiCache)
Redis is memory-bound. Cost scales with dataset size. If your hot dataset exceeds ~100GB, evaluate whether DynamoDB (which uses SSD) would be cheaper at your access pattern.
DDB
Recommended solution
DynamoDB (+ DAX for sub-ms reads)
Unlimited scale, zero ops, single-digit ms anywhere on earth.
auto-scales infinitely global tables: multi-region fully managed no SQL JOINs access patterns locked at design time hot partition problem exists

What to build

Design your access patterns first, then your schema — this is mandatory with DynamoDB. Partition key determines which shard your data lives on. GSIs (Global Secondary Indexes) enable different access patterns. DynamoDB Accelerator (DAX) is an in-process cache that brings reads to microseconds.

Real numbers

Read latency (strongly consistent)~1–3ms
Read latency with DAX<100µs
Max item size400KB per item
Cost per million reads (eventual)$0.25 (RCU)
Cost per million writes$1.25 (WCU)
Global Tables (multi-region) extra cost+2× write cost per region
Hot partition throttling: if one partition key (a celebrity user, a viral product) receives >3,000 RCU/s or >1,000 WCU/s, DynamoDB throttles it. Use composite keys (user_id + shard_suffix) to spread hot keys across partitions.
You cannot do ad-hoc queries on DynamoDB like you can on Postgres. "Show me all users who signed up last week" requires a GSI on created_at or a separate analytics store (Athena over S3).

What to do — in order

1. Run EXPLAIN ANALYZE on your slow queries. A missing index is 10× more likely than needing a replica. 2. Add pgBouncer — goes from 100 connections to 10,000 virtual, often free throughput gain. 3. Add one read replica; route all non-write queries there. 4. Add Redis for the top 5 most-repeated queries if needed.

Which one to pick

BigQuery

Serverless — pay per TB queried ($5/TB). Best for irregular or unpredictable usage. Automatic scaling. Google ecosystem.

Redshift

Best for sustained heavy analytics workloads. Provisioned clusters — predictable cost. Tight AWS integration (S3, Kinesis).

Snowflake

Best for data sharing across orgs. Separate compute and storage. Multi-cloud. Most expensive at scale.

ClickHouse Cloud

Best for real-time analytics where query latency matters. Sub-second vs minutes on the others. Less BI tool support.

What to build

Postgres remains the source of truth. Use Debezium (CDC) or an application-level dual-write to sync data to Elasticsearch. Write to Postgres first, sync to ES second. ES handles the search reads; Postgres handles everything else. OpenSearch is the AWS-managed fork — same API, no Elastic license fees.

Real numbers

Elasticsearch is an index, not a database. Never make it your source of truth. If your ES cluster goes down or gets out of sync, you must be able to rebuild it entirely from Postgres. If you can't, your architecture is wrong.

What to build

Write to Kafka topic (sub-millisecond ACK). Consumer reads from topic in batches of 100–500 rows, bulk inserts to Postgres. DB sees steady batched load instead of spikes. For pre-warm: scale consumer count before known traffic events. For SQS: same pattern but simpler — SQS → Lambda → Postgres.

Real numbers

Kafka producer ACK latency<1ms (async)
Kafka throughput (single partition)~100k msgs/s
Batch insert (100 rows) vs 100 singles10–50× faster
Consumer → Postgres drain rate~5–20k rows/s batched
Write latency added (end-to-end)50–500ms (async)
Confluent Cloud cost (basic)~$0.11/GB throughput
Your writes are now asynchronous. A user submits a form, gets a 200 OK, but their data isn't in the DB yet. This breaks "refresh immediately" UX. Solutions: return the write ID immediately from the queue, use optimistic UI updates, or use synchronous writes for user-facing actions and async only for background events.

Choosing the distribution column is the most important decision. user_id is usually right — queries that include user_id hit exactly 1 shard. Queries without it fan out to all shards. Never choose a low-cardinality column (status, country) — all writes for that value go to the same shard.
Alternative: CockroachDB or YugabyteDB give you distributed SQL with automatic sharding and rebalancing. More operational complexity but no manual shard management. CockroachDB handles ~10–50k writes/s per node and scales horizontally.

ScyllaDB vs Cassandra — choose ScyllaDB for new projects

ScyllaDB is a C++ rewrite of Cassandra. Same CQL query language and data model. 10× better throughput per node. Lower p99 latency. Better compaction strategies mean lower write amplification. Only reason to choose Cassandra: existing operational knowledge or 3rd party tooling that only supports Cassandra.

Real numbers

ScyllaDB write throughput (per node)~500k–1M writes/s
Cassandra write throughput (per node)~50–100k writes/s
Write p99 latency (ScyllaDB)<1ms
LSM write amplification10–30× (data written N× for compaction)
Read on partition key (cached)<1ms
Read on non-partition keyFull cluster scan — don't do this
ScyllaDB Cloud (3-node i4i.4xlarge)~$3,000/month
Write amplification is real. A Cassandra/ScyllaDB write hits: memtable → commit log → multiple SSTables during compaction. Actual disk write I/O is 10–30× the logical data size. Factor this into storage provisioning.

DynamoDB Accelerator (DAX)

DAX is an in-process Cassandra-compatible cache that sits between your app and DynamoDB. Reads that hit DAX return in microseconds vs milliseconds for DynamoDB directly. No code changes — DAX is a drop-in replacement for the DynamoDB client. Best for extremely hot read keys.

Architecture

Commands (writes) go to a fast append store — Kafka, EventStoreDB, or DynamoDB. An async consumer reads from the write store and builds one or more read models — a denormalised Postgres table, an Elasticsearch index, a Redis sorted set. Each read model is shaped exactly for one query pattern.

Real numbers

Write store (Kafka) throughput~1M events/s
Read model build lag100ms–5s behind writes
Read model query speedSub-ms (optimised for exact query)
Engineering complexity (1–10)8/10 — only when necessary
Only adopt CQRS when simpler architectures are genuinely exhausted. The eventual consistency between write and read models creates subtle bugs that are hard to detect and harder to fix in production. Start with the full Postgres stack first.

Golden rules
01Exhaust Postgres before migrating. Most "scaling problems" are missing indexes.
02Never run analytics queries on your OLTP primary.
03Redis cache solves most read problems in a day. DynamoDB migration takes weeks.
04Add a write queue (Kafka/SQS) before sharding. It buys time.
05Batch inserts: 100 rows in 1 INSERT is 10–50× faster than 100 individual inserts.
06Never make Elasticsearch your source of truth. It's an index.
07Design DynamoDB access patterns before the schema — not after.
